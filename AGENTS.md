# Project rules

- Every Studio shot needs both a start and an end frame (HTTPS only, enforced in the client and the shared studio-clip/contract.ts schema), because shots render independently between keyframes; chaining reuses a shot's end as the next start with no render wait. Primary is the default; StudioClipPanel auto-resubmits the identical 9-field payload (same seed) to backup only when primary fails or is unavailable, because backup has one worker. Shots hold multiple takes that are never overwritten; approving sets the active take used for stitching and re-anchors the next unapproved shot; started-but-failed jobs are kept as video-less takes so their cost is counted. Cost = worker execution seconds × one editable pool rate. Keep validation, QC and cost math in studioClipUtils so it is testable without GPU jobs.
- Studio clips use the existing rehost-video service before playback; keep the source on saving failure and isolate playback recovery in StudioClipPlayer so storage outages never discard completed shots.
- Studio shots and final sequences live in persisted ProjectContext so switching to Music does not discard shots; stitch through the dedicated studio-stitch function with a fixed endpoint and route/params envelope, keeping worker credentials server-side and final playback on StudioClipPlayer.

- The Director workspace uses dedicated Script, Storyboard, Director and Sequence routes under one persistent Dashboard/ProjectProvider; editable drafts belong in ProjectContext, and visited tools remain mounted to preserve in-flight work during navigation.
- Sequence UI lives in StudioSequencePanel, with optional music on the Sequence page; StudioClipPanel can embed it for regression coverage, and final sequence records retain their worker job ID for traceability.
